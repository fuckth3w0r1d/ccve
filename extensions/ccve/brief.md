挖掘一个 CVE，直到在调试容器里验证可行并产出 PoC。目标由你选定。下面所有路径都相对本仓库根目录。

## 一、目标硬性要求

目标仍在维护：最近 6 个月内有 commit 或 release。

安全上报渠道明确：属于某个 CNA 的覆盖范围，或接受通过 MITRE CNA-LR / GitHub advisory 转 CVE，能够获取 CVE 编号。

漏洞类型优先二进制 pwn，且有实际价值：优先网络协议栈与协议解析器、暴露在网络的中间件/服务组件、文件/媒体解析器等；要有清晰的网络输入入口，以二进制形式部署，或核心逻辑在 native 代码中。

不得基于已有修复 commit 挖掘：不能偷懒通过已有修复 commit 反推漏洞。

## 二、漏洞价值与真实性要求

目标是实现 RCE；至少也应是有实际价值的越界写或信息泄露。

必须以真实环境或远程攻击为前提：不能通过关闭 ASLR/PIE 等实际攻击无法实现的手段做本地特化 RCE。

应在官方源安装的包中实现，而非自行构建的包。

调试探测时可以做本地特化行为来挖掘，但利用链不能依赖这些本地特化条件，要确保远程真实环境可用。

## 三、选目标

先读 `board.md` 排除已经挖过的，再按第一节的硬门槛筛。优先级：

1. 网络协议栈与协议解析器。
2. 暴露在网络的中间件、守护进程、VPN 与网关。
3. 文件、媒体、文档解析器，要有网络投递路径。

不找过于热门的目标：撞车概率高。可以顺着已挖目标的相邻组件找——同厂商的兄弟产品、同一份代码的不同前端。

选中后就地做撞车检查，通过再投入审计时间。检索面：

- CVE 数据库：NVD、MITRE、发行版 tracker。
- 上游仓库的 issue、PR、commit message。
- 组件所在发行版的安全公告，以及 GHSA。
- 公开披露：博客、会议材料、oss-security。

检索词不能只用组件名，还要用协议名加解析动作、函数名、缺陷类型加模块名。

判定：已有 CVE 覆盖同一代码路径就换目标；覆盖相邻函数可以继续，但要写清区别；有未公开的修复 commit 则放弃。

## 四、目标目录

通过撞车检查后建 `work/<target>/`，包含：

```
state.md     当前假设、已排除的方向、下一步。每完成一个阶段覆盖一次。
journal.md   时间线，只追加。
src/         上游或发行版源码。
env/         目标容器的 Dockerfile 与 compose。
notes/       recon.md、finding.md、chain.md。
exp/         利用脚本。
logs/        容器日志、core、复现输出。
```

`notes/recon.md` 写撞车检查的结论。`journal.md` 记下目标、选它的理由、要审的入口。`board.md` 追加一行，状态 `active`。

目录建好后调用 `container` 工具的 `op` 为 `bind`，`target` 填目标名。之后所有容器操作都用这个绑定。

## 五、产出

PoC 通过验收后产出到 `../pocs/<target>/`（与本仓库同级），从 `templates/poc/` 复制骨架：

```
README.md            一段话概述 + 怎么跑 + 目录说明
docs/report.md       完整分析，中文
docs/report-en.md    英文
poc-<distro>/        Dockerfile、docker-compose.yml、target-init.sh、run.sh、exp/
img/
```

report 开头一段话概述，之后四个板块，中英逐节对应：

| 板块 | 内容 |
| --- | --- |
| 漏洞成因 | 根因所在的代码位置与解释，按缺陷分小节，附触发路径 |
| 影响 | 受影响的软件版本范围，各发行版实际打包的版本状态 |
| 利用分析 | 攻击者能拿到什么，利用链怎么走 |
| 修复建议 | 上游的修复方式，或者应该怎么改 |

## 六、验收

- ASLR、PIE、RELRO、Canary、NX 保持发行版默认值。
- 二进制来自官方源包。
- 攻击者只需要能连上端口。
- 重建容器后跑两次都成功。

通过后改 `board.md`：该目标状态改 `done`，`漏洞` 列填 CVE 编号或漏洞类型。然后 `goal({op:"complete"})`。
